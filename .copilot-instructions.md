## Development Environment

This project uses **Docker Compose** for development and execution. 

### Important Rules

1. **Never use npm/pnpm commands directly** when running the application
2. **Always use Docker Compose commands** instead
3. The application runs inside Docker containers, not on the host machine

### Common Commands

Instead of traditional npm commands, use:

```bash
# Start the application
docker compose up

# Start in detached mode
docker compose up -d

# Rebuild and start
docker compose up --build

# Stop the application
docker compose down

# View logs
docker compose logs -f

# Execute commands inside the container
docker compose exec app <command>

# Install dependencies (if needed)
docker compose exec app pnpm install

# Run tests
docker compose exec app pnpm test

# Run migrations
docker compose exec app pnpm migration:run
```

### Project Structure

- Main source code: `root_src/`
- Docker Compose configuration: `docker-compose.yaml`
- The app runs on NestJS framework with TypeScript

### When Making Changes

1. After code changes, the app should auto-reload (if configured with volumes)
2. If changes don't reflect, rebuild with: `docker compose up --build`
3. For dependency changes, rebuild the container

### Default Workflow

When asked to run, test, or start the application:
- ✅ Use: `docker compose up`
- ❌ Don't use: `npm start`, `pnpm start`, `npm run dev`, etc.

## Documentation Standards

**CRITICAL**: Before creating or modifying any documentation files in `root_src/docs/`, you **MUST** read these guides:

📖 **Read First**:
1. `root_src/docs/documentation-naming-convention-guide.md` - File naming standards
2. `root_src/docs/documentation-structure-guide.md` - Document structure & templates

### Quick Reference - Naming Convention

**Format**: `[scope]-[subject]-[type].md`

**Examples**:
```
✅ error-handling-domain-error-codes-guide.md
✅ validation-error-format-examples.md
✅ architecture-request-response-flow-documentation.md
```

**Rules**:
- All lowercase, use hyphens (`-`)
- Three components: scope + subject + type
- No underscores, no spaces, no camelCase

**Common Scopes**: `architecture`, `error-handling`, `validation`, `api`, `authentication`, `database`, `testing`, `[feature-name]`

**Common Types**: `guide`, `documentation`, `examples`, `quickstart`, `reference`, `tutorial`, `overview`

### Quick Reference - Document Structure

**CRITICAL**: All documentation **MUST** be:
- ✅ **Concise** - No fluff, straight to the point
- ✅ **Scannable** - Use headings, bullets, tables
- ✅ **Actionable** - Focus on "how to" not just "what"

**Required Sections** (All Documents):
1. Overview (2-3 sentences max)
2. TL;DR section
3. Code examples (where applicable)
4. Related documentation links

**Length Guidelines**:
- Quickstart: 50-150 lines
- Guide: 200-400 lines
- Examples: 100-300 lines
- Documentation: 300-800 lines

⚠️ **For complete templates, scope-specific requirements, and best practices**, always refer to:
- Naming: `root_src/docs/documentation-naming-convention-guide.md`
- Structure: `root_src/docs/documentation-structure-guide.md`
